# Instamart Customer Intelligence & Support Copilot

## Overview

A synthetic-data capstone in four connected parts. All data is fictional, generated by the supplied `generate_data.py`; the brand name only frames the scenario. All money is in INR. Every language-model call goes through the supplied offline `mock_llm.py`, so no API key, account or network is used.

| Part | Problem | What was built |
|---|---|---|
| A | Raw exports are untrustworthy | Audit, documented cleaning rules, SQLite database, 7 SQL queries, pandas cross-check |
| B | Which customers are valuable, which will lapse? | RFM + K-means segments, a leak-free lapse model |
| C | Support desk is buried in free-text tickets | Guarded triage: redaction, retries, output validation, token budget, routing |
| D | Policy lookups and simple refunds wait in a queue | TF-IDF policy assistant and a tool-calling refund agent with safety limits and resume |

Each part feeds the next: Part B reads Part A's clean CSVs, Part C routes with Part B's segment file, and Part D's agent reads Part A's database.

Layout: `generate_data.py` and `mock_llm.py` (supplied, unmodified) at the root; `src/` holds one script per task group (`a1_audit.py` ... `d_agent.py`) plus `common.py`; `sql/queries.sql`; `data/` (raw, clean, policies, `instamart.db`); `outputs/`; `state/` (agent checkpoints). Libraries: standard library, pandas, numpy, scikit-learn, joblib only. Work is on the single branch `main`.

### Cleaning rules and what each changed

Customers:

1. City: strip spaces and title-case. 24 raw spellings became 6 cities (Pune 227, Delhi 210, Bengaluru 197, Chennai 191, Hyderabad 191, Mumbai 184).
2. Gender: any of male/m (any case) becomes `male`, female/f becomes `female`, blank or other becomes `unknown`: female 610, male 560, unknown 30.
3. Age: 6 impossible ages (outside 10-100) set to missing; then all 67 missing ages (61 blank + 6 impossible) filled with the median age of the customer's city using `groupby().transform("median")`. Result: 0 missing, range 18-60.
4. `signup_date` converted to datetime (1,200 values).

Orders, in this order:

1. `order_ts` converted to datetime (13,084 values).
2. Exact duplicate rows removed: 119 rows (13,084 to 12,965).
3. Kept the record with the latest `order_ts` per `order_id`: 656 earlier `pending` records removed (12,965 to 12,309).
4. `order_amount` converted to numeric: 112 unparseable values (the 120 raw ones minus 8 that sat in rows removed by rules 2-3) became missing and were filled with `round(price_inr x quantity x (1 - discount_pct/100), 2)`. 0 missing afterwards.
5. `delivery_minutes`: 105 negative values (106 raw, one in a removed row) set to missing. For completed orders, 774 missing values (negatives plus originally blank) filled with the median of the order's product category among completed orders (Dairy 25.0, Electronics 25.0, Grocery 25.0, Personal Care 25.5, Snacks 25.0). Cancelled orders were left missing (1,199): a cancelled order was never delivered, so imputing a time would invent data.

After cleaning: 12,309 rows, one per `order_id`; 11,110 completed and 1,199 cancelled; no pending rows; 0 missing `order_amount`; 0 missing `delivery_minutes` among completed and 1,199 among cancelled; completed revenue INR 2,998,668.80.

### RFM table

### K-means (StandardScaler, `KMeans(n_clusters=K, n_init=10, random_state=42)`)

| K | Inertia | Silhouette | Inertia drop from previous K |
|---|---|---|---|
| 2 | 1820.8 | 0.465 | n/a |
| 3 | 1268.2 | 0.445 | 30.3% |
| 4 | 743.1 | 0.526 | 41.4% |
| 5 | 617.4 | 0.480 | 16.9% |
| 6 | 503.2 | 0.482 | 18.5% |
| 7 | 408.5 | 0.416 | 18.8% |
| 8 | 366.5 | 0.412 | 10.3% |

**Chosen K = 4.** The elbow is at K=4 (the biggest drop, 41.4%, then only 16.9%), K=4 has the best silhouette (0.526), and four named groups are something the business can act on. Inertia at K=8 is always lower than at K=2 because every extra centroid can only shrink the distances to the nearest centroid (it would reach zero with one cluster per customer). That is why inertia alone cannot choose K: it keeps falling whatever the true structure is.

### Lapse problem

Cutoff 2025-09-01. Cohort: every customer with at least one completed order before the cutoff (1,156). Label `lapsed` = 1 if there is no completed order from 2025-09-01 to 2025-09-30: 443 lapsed (38.32%). Features (only orders before the cutoff plus the clean customer table): recency, frequency, monetary, average discount_pct, cancellation rate, average delivery_minutes, favourite category, city, age, gender, tenure in days. Split with `train_test_split(test_size=0.2, stratify=y, random_state=42)`: 924 training rows (354 lapsed) and 232 test rows (89 lapsed).

**Leakage controls.** No order dated 2025-09-01 or later entered the features (asserted in code). The segment labels from the RFM clustering were not used as features. No encoder, scaler or resampler saw test rows: one-hot encoding (`drop="first"`, k-1 columns) and standardisation live inside a scikit-learn `Pipeline`, so they are fitted on training rows only (inside each cross-validation fold during tuning), and over-sampling touched training rows only. The code confirms no feature column has a missing value.

The scaler fitted on the training rows learned a frequency mean of 8.115, versus 8.029 over the full cohort; they differ because the training rows are a random 80% subset of the cohort and the scaler deliberately never sees the test rows.

### Models

| Model | Best parameters | Best CV F1 (lapsed) |
|---|---|---|
| Baseline: always "not lapsed" | n/a | test accuracy 61.6%, lapsed F1 0.00 |
| Logistic regression, `C` in {0.01, 0.1, 1, 10, 100} | C = 100 | 0.651 |
| Random forest, `max_depth` in {3, 5, 8}, `min_samples_leaf` in {5, 10, 20} | max_depth 5, min_samples_leaf 5 | 0.683 |

Test set, lapsed class as positive:

| Model | Precision | Recall | F1 | Confusion matrix [[TN, FP], [FN, TP]] |
|---|---|---|---|---|
| Tuned logistic regression | 0.644 | 0.652 | 0.648 | [[111, 32], [31, 58]] |
| Tuned random forest (selected) | 0.629 | 0.629 | 0.629 | [[110, 33], [33, 56]] |

**Choice.** I selected the random forest because it had the higher cross-validated F1 (0.683 versus 0.651); selecting on CV keeps the test set untouched. On the test set the two models are close (F1 0.629 versus 0.648, a difference of about two customers on 232 rows). Missing a customer who is about to lapse costs a lost customer, while wrongly targeting a loyal one costs only a coupon, so recall matters more than precision. Both tuned models catch only about 63-65% of lapsing customers, which is the reason to look at the balanced model below. The selected model's test F1 of 0.629 is above the required 0.55.

### Class-balance experiment

Over-sampling the training set only (216 randomly duplicated lapsed rows, `random_state=42`, giving 570 per class), then refitting the best logistic regression:

| Logistic regression trained on | Precision | Recall | F1 | Confusion matrix |
|---|---|---|---|---|
| original training set | 0.644 | 0.652 | 0.648 | [[111, 32], [31, 58]] |
| balanced training set | 0.589 | 0.854 | 0.697 | [[90, 53], [13, 76]] |

Recall moved most (0.652 to 0.854); precision fell (0.644 to 0.589). For the retention team this means catching 76 of the 89 lapsing customers instead of 58, at the price of contacting 53 loyal customers instead of 32. That is a good trade whenever a win-back offer costs much less than a lost customer.

### Interpretation, persistence, retention list

Top five random-forest feature importances: frequency 0.317, monetary 0.260, recency 0.112, cancel_rate 0.073, avg_delivery_minutes 0.049. Readings: how often someone orders is the strongest signal of staying; total spend is next; days since the last order adds some warning; repeated cancellations and slow deliveries point to friction.

Logistic-regression coefficients (standardised features; positive raises the lapse probability): frequency -1.698 (more orders strongly lowers lapse risk); monetary +0.285 (after accounting for frequency, higher total spend is not protective; the two are correlated, so read this sign with care); recency +0.040 (almost no extra effect once frequency is known).

The selected model is saved with `joblib.dump` to `outputs/lapse_model.joblib`; the reloaded model reproduces the original test predictions and probabilities exactly (checked in code).

`outputs/retention_list.csv` ranks the 40 Premium customers in the test set by predicted lapse probability and keeps the top 10 (probabilities 0.459 to 0.533). **0 of those 10 truly lapsed**; across all 40 Premium test customers 12 lapsed (30.0%, versus 38.4% in the whole test set). The Premium flag comes from whole-window RFM, which includes the September window that defines the lapse label, so the retention list is illustrative and not a leakage-free evaluation.

Re-applying the three patterns to the redacted texts finds 0 matches. The user message is exactly the redacted ticket text. Code asserts that no prompt sent to the model contains a pattern and that no empty or long ticket reached the model; both assertions passed in every run.

**Prompts.** Zero-shot (38 estimated tokens) and few-shot (123 tokens) both contain `CLASSIFY`, the four categories and a JSON-only reply format; the few-shot prompt adds an `EXAMPLES:` line with four labelled examples including a fraud one.

In every full run over the 156 eligible tickets there were 19 `TransientLLMError`s, all recovered by a retry, with every wait inside the allowed range (0.045 to 0.0575 s for retry 0); no ticket ended with a permanent error.

**Output validation.** Valid JSON with an allowed category gives `classified_json`; non-JSON text is searched with `re.findall(r"[a-z]+", text.lower())` and accepted as `classified_keyword` only if exactly one category word appears; anything else, including valid JSON with a category outside the list (`shipping`), becomes `flagged_invalid_output` for human review, never a guess.

## Part D

### Chunking and retrieval

Chunks of 40 words with 10 words of overlap (step 30; stop after the first chunk reaching the last word): 15 chunks in total.

| Document | Chunks (overlap 10) | Chunks (overlap 0) |
|---|---|---|
| refund_policy.txt | 4 | 3 |
| delivery_policy.txt | 3 | 3 |
| escalation_policy.txt | 3 | 2 |
| payment_policy.txt | 3 | 3 |
| privacy_policy.txt | 2 | 2 |
| total | 15 | 13 |

`TfidfVectorizer()` is fitted on the chunk texts; a query is transformed with the same fitted vectorizer and chunks are ranked by cosine similarity (`retrieve(query, k=3)` returns `source`, `score`, `text`). For `refund policy late delivery` the top three chunks all come from `refund_policy.txt` (scores 0.2719, 0.2514, 0.2454).

*TF and IDF.* Term frequency measures how often a word occurs in a chunk; inverse document frequency down-weights words that occur in many chunks, so rare, informative words dominate the score. *Limitation:* TF-IDF matches words, not meaning, so two phrasings with the same meaning but different words (for example "money back" versus "refund") can miss each other.

### Grounded answers and evaluation

`answer(question)` retrieves three chunks and sends two messages to `mock_llm.chat`: a system message containing `POLICY ASSISTANT` that tells the model to answer only from the context, and a user message `CONTEXT:` / chunks each prefixed with `[file.txt]` / `QUESTION:` / the question. Evaluation on `policy_eval.csv` (12 answerable, 2 not covered):

| Setting | Expected doc in top 3 (of 12) | Expected fact in answer (of 12) | Fallback "I could not find..." (of 2) |
|---|---|---|---|
| overlap 10 | 12 | 12 | 2 |
| overlap 0 | 12 | 10 | 2 |

With overlap 0 two questions break because the answer sentence is cut at a chunk boundary: "What delivery time makes a completed order eligible for a full refund?" (the retrieved chunk begins after "more than 45 minutes", so the answer is only "receives a full refund of the order amount.") and "How soon is money returned when a payment fails but is deducted?" (the chunk ends at "returned automatically", before "within 48 hours"). Overlap keeps a sentence whole in at least one chunk.

### Tools and the refund rules

Five tools are defined in `TOOLS_SPEC` (name, one-sentence description, parameter schema) and dispatched through `TOOL_MAP`: `get_order` (reads `data/instamart.db`; `{"error": "order not found"}` if missing), `search_policy` (returns `retrieve` output under `results`), `calculate_refund` (completed order delivered in more than 45 minutes gets 100% of the amount, otherwise 0), `issue_refund` and `escalate_to_human` (each appends one JSON line with timestamp and tool name to `outputs/refund_ledger.jsonl`).

Safeguards added in code, not left to the model: `issue_refund` refuses anything above INR 1000; and both ledger tools are idempotent per order, so a retry after a crash cannot pay twice (a repeat call returns the same result without a second ledger line).

### ReAct versus plan-and-execute

ReAct made one model call per step plus a final one, measured: S1 5 calls (1,172 tokens), S4 4 (825), S5 3 (502), S6 2 (182), S7 6 (3,330). Every call re-sends the whole history, so cost grows faster than the number of steps, as S7 shows. Plan-and-execute asks for the step list once and runs the tools without the model; my estimate is about 2 calls for S1 (plan and final answer), clearly fewer tokens.

Unexpected observations are where they differ. ReAct reads each result before choosing: S6 (NOT_FOUND) stopped after 2 calls and S5 (cancelled order) after 3 without computing a refund. A fixed plan would try to compute a refund for an order that does not exist or was cancelled, so it needs a replanning call whenever `get_order` returns an error or a cancelled status, and its issue step must become an escalation above INR 1000 (S3) or be dropped when the refund is 0 (S4). Four of the seven scenarios (S3 to S6) take such a branch.

I would keep ReAct for this workflow: it is short (five steps on the happy path), costs at most about 1,200 tokens per request, its branching depends on what the order lookup returns, and the iteration, token and time limits already cap the damage. Plan-and-execute pays off for long, predictable workflows with many tools.

## Limitations and Next Steps

- **Synthetic data and a mock model.** Segment sizes, churn and the 100% few-shot accuracy describe the generator and the keyword-driven mock, not real customers or a real language model.
- **Premium flag is post-hoc.** It comes from whole-window RFM that includes the September lapse window, so the retention list is illustrative and not a leakage-free evaluation. In this run the top-10 list contained 0 customers who truly lapsed, so it should not be read as evidence that the ranking works; a real use would compute the Premium flag from pre-cutoff data only.
- **Lapse model.** The best logistic-regression `C` (100) sits at the edge of the grid, so a wider grid could help. Delivery-time medians used to fill missing values in Part A were computed over the whole window (values of 25.0 to 25.5), a negligible but real use of later data. Only 232 test rows, so differences of about 0.02 in F1 are within noise.
- **Agent.** The agent does not check that an order belongs to the requesting customer, and the 7-day refund window is not enforced (the brief treats all requests as inside it). On resume the time limit restarts. Checkpoints are written after tool observations, so a crash during a tool call relies on the tool being idempotent, which the ledger tools are.
- **Retrieval.** TF-IDF is lexical; synonyms are missed. Next steps: stemming or embeddings, a larger evaluation set, and a re-ranking step.
- **Triage.** "Rule-validated" labels can still be wrong; next steps are sampling validated tickets for human audit and confidence thresholds.
